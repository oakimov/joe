# JOE Editor — Markdown WYSIWYG Enhancement

## Project Overview

JOE (Joe's Own Editor) is a terminal-based text editor written in C, version 4.8. This project adds a toggleable Markdown view mode that hides markup delimiters, renders visual formatting (bold, italic, headings, tables), and emits clickable hyperlinks (Phase 1), with advanced rendering like Unicode table borders and nested syntax highlighting in code blocks (Phase 2).

**Repository:** https://github.com/oakimov/joe (fork of https://github.com/joe-editor/joe)
**Current branch:** `markdown`

Full task breakdown: `plans/TODO.md`
Feasibility analysis: `plans/markdown-wysiwyg-feasibility.md`

## Build

From a clean checkout (no generated files):

```sh
autoreconf -i && ./configure CFLAGS="-O3 -flto -DNDEBUG" LDFLAGS="-flto" --prefix=/opt/local && make
```

If `configure` already exists:

```sh
./configure --prefix=/opt/local && make
```

Requires: C compiler, standard libc, terminfo/termcap, GNU autoconf/automake. No external dependencies.

### Auto-stringify (builtins.c)

`joe/builtins.c` is generated by `joe/util/stringify` from a specific set of source files defined in `joe/Makefile.am`. The default file list is: `rc/joerc`, `rc/ftyperc`, `syntax/c.jsf`, `colors/default.jcf`, `syntax/comment_todo.jsf`, `syntax/filename.jsf`, `syntax/context.jsf`, `syntax/md.jsf` (the last one added by this project). Additional files can be included via `./configure --enable-extra-builtins="../syntax/python.jsf ../syntax/html.jsf"` or overridden at make time with `make EXTRA_BUILTINS="..."`. A custom rule in `joe/Makefile.am` automatically re-runs stringify during `make` when any of these files changes. The build order is: `rc/` built first (generates `rc/joerc` from `rc/joerc.in`), then `util/stringify` built (SUBDIRS=util), then `builtins.c` regenerated, compiled, and linked. **After editing any of these source files, a plain `make` picks up the changes — no manual stringify step needed.** Note: `builtins.c` is ~2.5K lines. This is expected — it embeds selected rc configs and syntax DFA files so JOE can function without any external config files. Do not add more files to the default list unless they are needed at runtime without installed config.

### Clean Build State

To remove all generated artifacts (configure, Makefiles, compiled objects, etc.) and return to a source-only state:

```sh
make distclean && rm -f configure aclocal.m4 config.guess config.sub depcomp install-sh missing compile
```

## Post-Feature Code Review

After completing any feature, critically review all changed code before committing:

- **Memory leaks**: every `joe_malloc`/`joe_realloc` must have a corresponding `joe_free` on all paths (including error/early-return paths)
- **Buffer overflows**: all array accesses must be bounds-checked; `realloc` failure must not leave dangling pointers
- **Security issues**: sanitize all external input (URLs, file paths, terminal escape sequences); prevent format string and injection vulnerabilities
- **Redundant code**: remove dead functions, unused variables, duplicate logic, unreachable branches
- **Extreme inputs**: verify correct behavior with huge files (10,000+ lines), extremely long lines (1MB+), pathological Unicode (zero-width, combining, surrogate), and OOM conditions (malloc/realloc returning NULL)
- **Unlikely scenarios**: terminal resize during rendering, concurrent buffer modifications, nested syntax call stack overflow, malformed markdown constructs, empty files, files with no trailing newline
- **Compiler warnings**: zero warnings allowed (`-Wall -Wconversion -Wunused -Wshadow` etc.) - this includes preexisting warnings. Fix them before starting work on new features.

Fix every issue found regardless of how small it is. Do not introduce new issues in the process.

## Working on This Project

This codebase has well-structured components and many independent tasks. When working on features that can be executed in parallel, use **subagents** to speed up work:

- **Independent features** within a phase (e.g., Features 1.3–1.9 in Phase 1) can be tackled simultaneously by spawning multiple subagents
- **Cross-component analysis** (comparing files, checking references, searching patterns) is faster when delegated to independent subagents
- **Testing multiple scenarios** (different terminals, color depths, file sizes) can be parallelized across subagents

Example: When implementing Phase 1, spawn separate subagents for:
- Feature 1.3 (heading delimiter hiding)
- Feature 1.4 (inline style delimiter hiding)
- Feature 1.5 (code block rendering)
- Feature 1.6 (link rendering with OSC 8)
- Feature 1.7 (blockquote and list rendering)
- Feature 1.8 (horizontal rule substitution)

Each subagent independently implements, tests, and documents their feature. This approach is especially effective for this project because the rendering pipeline (`lgen()` → `outatr()` → `set_attr()`) and DFA syntax file (`md.jsf`) are modular.

## Architecture

### Rendering Pipeline

```
Syntax DFA (.jsf file)
  → HIGHLIGHT_STATE per line (cached in lattr_db)
    → lgen() in bw.c dispatches:
      ├─ lgen_core() — standard rendering engine (per-character attributes)
      └─ lgen_view() — Markdown view mode (parse → build hide map → lgen_core)
        → attr[] array (per-cell attributes)
          → outatr() / set_attr() in scrn.c emit escape sequences
            → terminal renders
```

Each character cell gets its own attribute value (foreground, background, bold, italic, underline, etc.). This is per-pixel rendering for a character grid — not "one color per line."

### Key Capabilities Already Present

- **Truecolor 24-bit RGB**: `scrn.c` detects `Tc` or `truecolor` terminfo flag, emits `\e[38;2;R;G;Bm` / `\e[48;2;R;G;Bm`
- **Bold, Italic, Underline, Dim, Inverse**: `set_attr()` in `scrn.c:166` handles all standard attributes
- **Strikethrough / Double underline**: `scrn.c:662-666` sets escape sequences `\e[9m` / `\e[21m` for ANSI terminals
- **Per-line background color**: `bg_curlin` in `bw.c:13` (current line highlighting)
- **OSC 8 hyperlinks**: `OUT_osc8` / `END_osc8` macros at `bw.c:429-430`
- **256-color palette**: Gruvbox and other schemes use `.colors 256` with palette indices
- **Nested syntax (call mechanism)**: `c.jsf:121-144` shows how to call sub-syntaxes via `call=filename.subroutine()`
- **Line attribute cache**: `lattr.c` caches `HIGHLIGHT_STATE` per line, handles multi-line constructs
- **Full UTF-8**: Unicode box-drawing (U+2500-U+257F), bullets, checkmarks all work

## Syntax DFA Format (.jsf)

A minimal reference for editing `.jsf` files:

```
# Color class definitions (map to .jcf scheme colors)
=Idle
=Bold        +Keyword          # inherits from Keyword color class
=Headline    +Title +Preproc   # can combine multiple

# State machine states
:state_name ColorClass
    *       next_state                # default transition
    "x"     other_state  recolor=-2   # match char 'x', recolor 2 chars back
    "ab"    third_state  noeat        # match 'a' or 'b', don't consume char
    "\n"    line_start

# Key transition options:
#   noeat            — don't consume this character, let next state process it
#   recolor=-N       — recolor N characters backward
#   recolormark      — recolor from mark to current position
#   mark / markend   — set/remove bookmark for recolormark
#   buffer           — start buffering characters
#   strings          — switch to string matching mode
#   call=file.sub()  — call sub-syntax (nested DFA)
#   rtn              — return from sub-syntax call
#   save_s           — save buffered string for string matching
```

For the full specification, see `syntax/jsf.jsf` (the syntax file for syntax files).

## Implementation Approach

### Phase 1 — View Mode (C changes + jsf rewrite)

**Status: Infrastructure and rendering complete through Feature 1.8. Features 1.9 (tables) and 1.10 (cursor mapping) remain.**

A `viewmode` flag was added to `OPTIONS` struct in `b.h` (not `BW` — it's a per-buffer option). `syntax/md.jsf` rewritten with full DFA for all markdown constructs. In `bw.c`, when `viewmode` is active, `lgen()` dispatches to `lgen_view()` which:
1. Parses the line to get syntax attributes via `parse()`
2. Reads raw line bytes into a local buffer
3. Identifies line type (heading, fence, blockquote, rule, or inline content) and marks delimiter positions in `viewmode_hide[]` bitmap
4. Delegates to `lgen_core()` which renders hidden delimiters as spaces

**Hidden in view mode:** heading `#` + trailing space, fenced code block fence lines (```/~~~), blockquote `>` + space, horizontal rules (3+ matching chars), `**`/`__` bold, `*`/`_` italic, `~~` strikethrough, `` ` `` inline code backticks, link `[`/`](`/`)` delimiters.

**Not yet implemented:** table rendering, cursor position mapping, OSC 8 hyperlinks for links, Unicode substitutions (bullets, horizontal rules, blockquote bars), nested blockquote rendering, task list checkboxes, bold+italic (`***`) handling.

**Critical challenge:** cursor position mapping (Feature 1.10). When delimiters are hidden, the displayed column doesn't match the buffer column. Need a mapping table or offset tracking in `lgen()`.

### Phase 2 — Advanced Rendering (C changes)

Unicode box-drawing table borders, nested syntax highlighting in fenced code blocks using the `call` mechanism, alternating row backgrounds, paragraph spacing.

## Key Constraints

- **C only, libc only** — no C++, no external libraries
- **Terminal compatibility** — must degrade gracefully: truecolor → 256-color → 16-color → attributes only
- **No buffer modification** — view mode changes rendering only, never modifies the underlying text
- **Performance** — must handle 10,000+ line files without noticeable lag
- **Existing behavior preserved** — when `view_mode` is off, rendering must be identical to current version
